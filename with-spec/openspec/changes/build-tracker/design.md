# Design

## Context

Новый проект: в рабочей папке пока нет кода, есть только OpenSpec-артефакты. См. `proposal.md` и `specs/tracker/spec.md`. Ограничения из `brief.md`: вариант B, нет CDN, внешних библиотек и API-ключей; всё должно работать как статические файлы, а логика — проверяться через `node:test` без браузера.

## Goals / Non-Goals

**Goals:**

- Отделить чистую доменную логику от DOM, чтобы T1–T5 проверялись в Node без браузера.
- Сделать единственный источник истины для задач и вычислять отображаемые итоги из него, а не из видимого списка.
- Обеспечить предсказуемую валидацию часов без проблем с плавающей точкой.
- Оставить интерфейс простым и доступным на ширине 390 px.

**Non-Goals:**

- Серверная часть, синхронизация, аккаунты и сетевые API.
- Сборка, бандлеры, фреймворки и внешние зависимости.
- Автоматизированная проверка вёрстки в браузере (в рамках этого изменения вёрстка проверяется вручную).
- Расширенная работа с датами, неделями и напоминаниями — только задачи с часами.

## Decisions

### Модульное разделение `domain.mjs` / `app.mjs`

`domain.mjs` содержит чистые функции без доступа к DOM и `localStorage`: стартовые данные, валидацию, подсчёт часов, прогресс, фильтрацию, добавление/удаление/переключение. `app.mjs` отвечает за состояние, DOM, рендер, обработку формы и опциональное хранилище.

Альтернатива — один файл со всей логикой — отвергнута: приёмочные тесты T1–T5 импортируют функции из `domain.mjs`, и смешивание с DOM сделало бы их хрупкими.

### Неизменяемые операции над списком

`addTask`, `removeTask`, `toggleTask` возвращают новый массив и не мутируют аргумент. Идентификаторы новых задач генерируются в `app.mjs` (например, `crypto.randomUUID()` с запасным вариантом), а `domain.mjs` принимает готовый объект.

Альтернатива — мутировать массив на месте — отвергнута: неявные побочные эффекты усложняют тесты и повторный рендер.

### Валидация часов через шаг 0,5

Часы принимаются как строка из формы. Пустая строка после `trim` — ошибка «укажите часы», а не ноль. Значение приводится к числу; проверяется, что оно конечное, `>= 0.5`, `<= 24` и что `value * 2` — целое (допуск на погрешность). Название проверяется после `trim`.

Альтернатива — `input[type=number][step=0.5]` без ручной проверки — отвергнута: браузерная валидация не мешает отправить пустое или дробное значение и не даёт единого поведения в тестах.

### Прогресс только из всех задач

`totalHours`, `doneHours` и `computeProgress` принимают полный массив задач. Фильтр применяется только в `filterTasks` для рендера списка. `computeProgress` при нулевой сумме часов возвращает `0` до деления, что исключает `NaN`/`Infinity`. Округление — `Math.round`.

Альтернатива — считать прогресс по видимым задачам — противоречит требованию и приёмочному сценарию T2.

### Состояние и рендер в `app.mjs`

Состояние: `tasks`, `filter` (`all`/`active`/`done`), ошибки формы. На каждое действие выполняется пересчёт и полный рендер списка, итогов и прогресса. Это достаточно для малого списка и исключает рассинхронизацию.

### Опциональный `localStorage`

При старте `app.mjs` пытается прочитать сохранённые задачи. Все обращения к `localStorage` оборачиваются в `try/catch`; при ошибке показывается понятное сообщение, а трекер продолжает работать с данными в памяти без дальнейших попыток записи. Если сохранённых данных нет или они повреждены, используется стартовый набор.

Альтернатива — обязательное хранилище — отвергнута: `brief.md` называет улучшение необязательным, а падение хранилища не должно ломать трекер.

### Тесты на встроенном `node:test`

`tests/acceptance.test.mjs` импортирует только `domain.mjs` и проверяет T1–T5: стартовые 8/2/25, фильтр «активные» (2 задачи, прогресс 25), ошибки ввода, удаление всех (0 ч/0%), отметку «Практики» (6/8, 75%). Запуск: `node --test`.

### Доступность и мобильная ширина

Семантическая разметка: `main`, `form` с `label` для каждого поля, `button` с текстом, список задач с чекбоксами и кнопками удаления с доступными именами. CSS без фиксированной ширины, `max-width: 100%`, `box-sizing: border-box`, переносы длинных названий. Проверка 390 px — ручная.

## Risks / Trade-offs

- [Ручная проверка вёрстки на 390 px не автоматизирована] → в задачах и отчёте явно разделять выполненные и предложенные проверки, не заявлять запуск браузера без него.
- [Повреждённые данные в `localStorage`] → валидировать структуру при чтении и откатываться на стартовый набор.
- [Погрешность плавающей точки при шаге 0,5] → проверять `value * 2` на целочисленность с малым допуском.
- [Полный рендер на каждое действие] → приемлемо для списка учебных задач; при росте списка можно перейти к точечному обновлению.
- [Опциональный `localStorage` может быть недоступен в приватном режиме] → обрабатывать исключения и продолжать в памяти, показывая сообщение.

## Migration Plan

Не требуется: проект создаётся с нуля, существующих данных и пользователей нет. Откат — удаление добавленных файлов.
